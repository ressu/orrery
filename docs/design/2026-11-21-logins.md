# Authorization: user logins

**Decision (2026-11-21):** people log in with a name, and their role comes from `orrery.toml`.
The role table is the same one that keys and networks use. There are three ways to log in:
- a local password, which orrery checks;
- a header from a trusted proxy, so a proxy such as oauth2-proxy with Dex can log users in;
- an agent, such as a future `orrery-ldap`.

Tokens keep Moonraker's format, so Fluidd needs no change.

**Status (2026-11-21):** approved by the user. Local users, tokens, one-shot tokens,
`force_logins`, the lockout, the import, and proxy logins are built. Agent sources, groups,
and OIDC come later.

This note builds on [2026-11-20-authorization.md](2026-11-20-authorization.md), which covers
roles, networks, proxies, and keys. Today `access.login` returns an error, and a browser on a
network without a role gets only a 401 (`no-logins` in `docs/regressions.md`). Fluidd's
Authentication section stays hidden, since orrery doesn't report the `authorization` component.

Scope of this step:

- **In:**
  - local users;
  - proxy logins;
  - roles for users;
  - Moonraker's tokens: logins, refresh, and one-shot tokens;
  - `force_logins` and `max_login_attempts`;
  - the user endpoints;
  - importing Moonraker's users.
- **Designed here, built later:** login sources that are agents, with LDAP as the first.
- **Later:** groups, OIDC inside orrery, and orrery editing `orrery.toml` to give users roles.

## Principles

The authorization note's principles still hold. Three of them decide most of this note:

- **The config decides who may do what.** A user's role comes from `orrery.toml`, whichever
  source they logged in with. The database holds only what can't be in the config: password
  hashes and signing keys.
- **No passwords in the config folder.** printerkeep and Klipper-Backup copy that folder to a
  git repository.
- **Small by default.** The main binary has only local passwords and proxy logins. Anything
  with a large library, such as LDAP, runs as an agent and is built only when someone needs it
  (user, 2026-11-21).

## Login sources

Each user has a source, as in Moonraker, where `access.login` takes a `source` and checks that it
matches the user's (`moonraker/components/authorization.py:552`).

| Source | Who checks the password | Built in |
|---|---|---|
| `local` | orrery, against a hash in its database | Yes |
| `proxy` | The proxy, before the request reaches orrery | Yes |
| An agent's source, such as `ldap` | The agent | No: the agent is a separate program |
| `orrery` | Nobody: keys and agents' keys, listed but never logged in | Yes |

- **Local users have the source `local`,** wherever they came from, imported or not: orrery
  owns them (user, 2026-11-21). Moonraker's replies call them `moonraker`, unless
  `[moonraker_compat] user_source_fix` is off (see the authorization note's "Moonraker
  compatibility"). Fluidd needs that name: it sends `moonraker` when it doesn't know better
  (`fluidd/src/api/socketActions.ts:989`), and it enables the delete and password buttons only
  for that source (`src/components/settings/auth/AuthSettings.vue:61`,
  `src/components/layout/AppUserMenu.vue:38`). orrery's own endpoints and the CLI say `local`.
  The keys' source stays `orrery`, as the authorization note decided.
- **`default_source`** picks the source when a login names none, as in Moonraker. It's the
  local source unless set.
- **`access.info`** lists the sources that are on in `available_sources`. Fluidd shows a
  source picker when there's more than one (`src/components/common/Login.vue:54-63,129`).
  `proxy` is never in the list, because nobody logs in to it with a password.
- **Local passwords can be turned off,** with `local_logins = false`. The user plans to log in
  through Dex, not with local passwords (user, 2026-11-21). With local logins off, `access.login`
  refuses the local source and Fluidd's add-user button gives an error. Imported users
  stay in the database, but they can't log in until local logins are on again.

## Roles for users

```toml
[authorization]
default_role = "viewer"        # for users who log in but aren't listed; not set: refused

[authorization.users]
admin = ["sami"]
operator = ["guest", "kid"]
```

- **`[authorization.users]` lists the users for each role,** the same shape as keys and
  networks. A role with one user may give it as a string. A name listed twice is an error that
  names both roles.
- **The role belongs to the name, whatever the source.** If `sami` is listed under `admin`,
  then `sami` is admin whether they logged in with a password, through the proxy, or through
  LDAP. One stored user has one source, as in Moonraker, so a local `sami` and an LDAP `sami`
  can't both exist.
- **A user who isn't listed gets `default_role`.** It isn't set by default, so the login is
  refused: "orrery.toml doesn't give the user guest a role. An admin can add them under
  [authorization.users]." The message doesn't list who is in the config.
- **Without `[authorization.users]`, local users are admin,** as every Moonraker user is. That
  keeps a printer set up with a `moonraker.conf` working after an import. orrery logs a warning
  at startup when there are local users and no list. Proxy and agent logins need the list:
  without it, they're refused. A proxy can let in anyone it knows, such as any Google account,
  and none of them should get admin by default.
- **A login adds rights; it never takes any away** (user, 2026-11-21). A connection's role is
  the higher of its network's role and its user's role. A viewer network where `sami` logs in
  gives admin. An admin network where `guest` logs in stays admin.
- **`force_logins = true` makes networks give nothing,** so every browser has to log in. Keys,
  the unix socket, and agents that orrery starts work as before. Moonraker applies
  `force_logins` only once a real user exists (`authorization.py:402,906`). orrery applies it
  whenever it's set, because the rules come from the config. With `force_logins` and no way to
  log in, orrery logs a warning.
- **A user can't have a key's name.** The user list shows keys too, so `homeassistant` can't be
  both. A clash between `[authorization.users]` and `[authorization.keys]` is a config error,
  and adding a local user with a key's name is refused.
- **Groups come later.** Dex supports groups, but the user's Dex isn't set up to send them, since
  nothing has needed them yet (user, 2026-11-21). The lists keep the `group:` prefix free for
  them: `admin = ["group:printer-admins"]`. A user name that starts with `group:` is an error
  until then.
- **Startup log:** one line with the users by role, and one line with the login sources that
  are on.

## Local users

- **Storage.** Users live in a redb table of their own, next to the keys' secrets, where
  `server.database.*` can't reach them. Each row holds the user's name, source, creation time,
  password hash, and signing key. The role isn't stored: it comes from the config.
- **Hashing.** New passwords use Argon2id with the parameters OWASP recommends: 19 MiB of
  memory, 2 passes, and 1 lane. That takes a fraction of a second on a Raspberry Pi; the time is
  measured on bluev2 before the code is merged. Imported users keep Moonraker's PBKDF2-SHA256
  hash, with 100,000 iterations (`authorization.py:69,537`). orrery replaces it with an Argon2id
  hash at the user's next successful login.
- **Adding and deleting.** Fluidd's buttons call `access.post_user` and `access.delete_user`
  (`src/api/socketActions.ts:1034,1046`). They work for an admin only (user, 2026-11-21); in
  Moonraker any authorized client can use them. They make or remove the user and password; the
  role still comes from the config. A new user that the config doesn't list can log in only if
  `default_role` is set, and orrery's log says so when the user is added. As in Moonraker, a user can't delete
  themselves.
- **Changing a password.** Any logged-in user can change their own, with
  `access.user.password` (`socketActions.ts:1057`). It needs the old password, as in Moonraker
  (`authorization.py:480`).
- **The CLI.** An admin without a browser uses the unix socket:

  ```
  orrery user list
  orrery user add <name>
  orrery user delete <name>
  orrery user password <name>
  ```

  `<name>` is the user's name. `orrery user list` shows the users with their source, their role
  from the config, when they were added, and whether they have tokens that work. Adding a user
  makes tokens, as in Moonraker, and logging out ends them. The command asks for the password
  and doesn't echo it. It never takes the password as an argument, so the password stays out of
  the shell's history.

## Proxy logins

A proxy in front of orrery can log users in itself and pass the user's name in a header. That's
how logins through Dex work: oauth2-proxy, or Caddy with `forward_auth`, sends the browser to
Dex and lets the request through once Dex has logged the user in (user, 2026-11-21). Fluidd
needs no change, and orrery needs no OIDC code.

```toml
[authorization.proxy_login]
header = "X-Forwarded-User"
```

- **The header is read only from a trusted proxy,** one in `trusted_proxies`. From any other
  address, orrery ignores it and logs a warning once, as it does for `X-Forwarded-For`. Setting
  `[authorization.proxy_login]` without `trusted_proxies` is a config error.
- **The proxy must remove the header** when a client sends it, or anyone could claim any name.
  - oauth2-proxy sets `X-Forwarded-User`, `X-Forwarded-Email`, `X-Forwarded-Preferred-Username`,
    and `X-Forwarded-Groups` with `--pass-user-headers`, which is on by default. It strips them
    from the client's request when it sets them (`--skip-auth-strip-headers`, on by default).
  - Caddy's `forward_auth` copies headers from the auth server's reply with `copy_headers`.
    Authelia's example copies `Remote-User`. Caddy's docs don't say whether a client's copy is
    removed first, so the example in the docs adds `request_header -Remote-User` before
    `forward_auth`.
- **No header, no user.** A request from the proxy without the header gets only its network's
  role, never a default user. So a misconfigured proxy fails closed for logins. The authorization
  note's warning about a proxy that has a network's role still applies.
- **Each request carries the user.** The websocket gets its user when it opens, and HTTP
  requests, such as uploads and downloads, each have the header. So proxy users need no tokens.
  Fluidd connects, calls `server.connection.identify` without a token, and is let in.
  `access.info` reports `trusted: true` for them, so Fluidd's logout keeps them signed in, as it
  does on a trusted network (`src/store/auth/actions.ts:99-101`).
- **Logging out happens at the proxy.** orrery can't end the proxy's session. `access.logout`
  from a proxy user returns an error that says to log out at the proxy, such as oauth2-proxy's
  `/oauth2/sign_out`.
- **Passwords are the proxy's too.** `access.user.password` from a proxy user says that the
  proxy's login service keeps the password.
- **A proxy user's name** follows the rules for local users' names, so a proxy can't name
  `_TRUSTED_USER_` or `agent.spoolman`. orrery logs each proxy user once, when they first come in.
- **Proxy users aren't stored** (user, 2026-11-22). orrery takes the name from the header on
  each request, and the role from `[authorization.users]`. So they don't appear in
  `access.users.list` or `orrery user list`, and a user the proxy forgets doesn't linger in
  orrery. Their session is the proxy's, so logging out happens only at the proxy.

## Login sources that are agents

An agent can check passwords for a source of its own. LDAP is the first example (user,
2026-11-21). It's designed here and built when someone needs it.

```toml
[agent.ldap]
command = "~/orrery/agents/orrery-ldap"
login_source = "ldap"
```

- **The call.** The agent registers `/agent/ldap/login` with POST, like any agent endpoint
  (see [2026-11-15-plugin-interface.md](2026-11-15-plugin-interface.md), "The agent section").
  For a login with `source: "ldap"`, orrery calls it with `{username, password}`. The agent
  answers `{ok: true}`, or an error. Later it can add `groups`.
- **Only the unix socket.** The password goes to the agent, so a login source must be an agent
  that orrery starts, or one that connects over the unix socket. A remote agent can't be a
  login source.
- **Timeout.** If the agent doesn't answer within 10 seconds, the login fails with "The ldap
  login source didn't answer". If it isn't connected, the login fails with "The ldap login
  source isn't running".
- **Users are stored at their first login,** with the agent's source and no password. That's
  where their signing key lives, as Moonraker does for LDAP users (`authorization.py:522-531`).
- **Changing the password** of an agent's user is refused, as Moonraker refuses it for LDAP
  (`authorization.py:490`).

## Tokens

Tokens keep Moonraker's format (user, 2026-11-21), so Fluidd's code for them works unchanged.
Imported users log in again, since their signing keys aren't imported.

- **Access and refresh tokens** are JWTs signed with EdDSA (`authorization.py:73-77`):
  - The header is `{"alg": "EdDSA", "typ": "JWT", "kid": <the user's key ID>}`.
  - The payload is `iss`, `aud: "Moonraker"`, `iat`, `exp`, `username`, and `token_type`, which
    is `access` or `refresh` (`authorization.py:640`).
  - The issuer is `http://<hostname>:<port>` (`authorization.py:157`). An imported token is
    valid only if orrery has the same host name and port as Moonraker had.
  - An access token lasts 1 hour. A refresh token lasts `login_timeout` days, 90 by default.
- **Where clients send them:** `access_token` in `server.connection.identify`; on HTTP, an
  `Authorization: Bearer` header, an `X-Access-Token` header, or `?access_token=`
  (`authorization.py:779`). orrery never logs a token; Moonraker logs one that fails to decode
  (`authorization.py:797`).
- **Each user has a signing key,** stored with the user. Logging in makes one if the user
  doesn't have one.
- **Logging out ends every session of that user,** on every device, because it forgets the
  signing key, as in Moonraker (`authorization.py:374`). orrery sends
  `notify_user_logged_out`, and Fluidd logs out when it gets one (`src/store/auth/actions.ts:125`).
- **Deleting a user, or changing their password, also ends their sessions.** Deleting forgets
  the signing key, as in Moonraker. Changing a password makes a new signing key; Moonraker
  keeps the old one, so stolen tokens would keep working. The connection that changed the
  password stays logged in. Both take rights away from the user's other open connections at
  once, as rotating a key does.
- **One-shot tokens** are Moonraker's: 20 random bytes in base32, valid for 5 seconds, for one
  use, from the address that asked for one (`authorization.py:61,772,846`). A one-shot token
  carries the rights of the connection that asked for it. orrery reads it from `?token=` on
  HTTP requests and on the websocket's upgrade, as Moonraker does. A token that isn't valid is
  ignored, so the request keeps its own rights. One from another address is logged.

## Endpoints

| Endpoint | Needs | Differs from Moonraker |
|---|---|---|
| `access.info` | Nothing | `login_required` is `force_logins`; `trusted` is true for a proxy user |
| `access.login` | Nothing | Refused for a user without a role |
| `access.refresh_jwt` | Nothing | None |
| `access.logout` | A user | A proxy user is told to log out at the proxy. A websocket goes back to its network's rights; in Moonraker it has none |
| `access.get_user` | `viewer` | Returns the user, or the trusted or API key user, as in Moonraker |
| `access.post_user` | `admin` | Any authorized client in Moonraker |
| `access.delete_user` | `admin` | Any authorized client in Moonraker |
| `access.users.list` | `admin` | Any authorized client in Moonraker; also lists keys and agents |
| `access.user.password` | A user | Makes a new signing key |
| `access.oneshot_token` | Any role | None, once orrery checks the tokens |
| `access.get_api_key`, `access.post_api_key` | `admin` | As in the authorization note |

Fluidd calls the user endpoints under the names above (`src/api/socketActions.ts:970-1066`).
Moonraker registers them as `/access/user` with GET, POST, and DELETE (`authorization.py:254`),
so orrery serves both forms, as it does for other endpoints with two names.

- **`access.users.list`** lists local users and agents' users, each with their source and
  creation time. Keys and agents' keys are also in the list, with source `orrery`, as the
  authorization note decided, and so is the `moonraker` key, which Moonraker hides as
  `_API_KEY_USER_` (`authorization.py:470`). A key that works should be listed somewhere (user,
  2026-11-21).
- **Notifications:** `notify_user_created`, `notify_user_deleted`, and
  `notify_user_logged_out`, which Fluidd handles (`src/store/socket/actions.ts:396-406`).
- **The `authorization` component** shows up in `server.info` from this step on. That turns on
  Fluidd's Authentication section (`src/views/Settings.vue:80`) and its loading of the user
  list and API key (`src/globals.ts:271`, `src/store/auth/actions.ts:20-31`). Fluidd loads all
  three together and needs each one to succeed. So an operator, who can't list users, gets an
  error there. That goes in `docs/frontend-issues.md`.

## Limiting guesses

- **`max_login_attempts`** counts failed logins for each client address, as in Moonraker
  (`authorization.py:355-372,860`). Behind a proxy, that's the address the proxy passes on.
- **A lockout ends,** unlike Moonraker's, which lasts until a successful login or a restart.
  After `max_login_attempts` failures, logins from that address are refused for
  `login_lockout` minutes, 15 by default. A successful login clears the count.
- **The count isn't stored,** so a restart clears it.
- **Log lines:** each failed login logs the name tried, the address, and the reason, such as
  "unknown user" or "wrong password", at info. A lockout logs one warning when it starts. The
  reply to the client doesn't say which part was wrong: "Wrong user name or password."

## Import

`orrery-import` already reads Moonraker's `authorized_users` table for the API key
(`crates/orrery/src/import/mod.rs:223`). It also copies the users, which updates `import-gaps`
in `docs/regressions.md`:

- **Name, source, and creation time.**
- **Not the signing key** (`jwt_secret` and `jwk_id`). Users log in again after the switch,
  with the same password, and get a new key. Keeping their sessions isn't worth copying key
  material (user, 2026-11-21).
- **The password hash and salt.** The user expects few people to import passwords, and would
  rather drop them than make the binary bigger (user, 2026-11-21). Checking PBKDF2 adds about
  6 KB (see [Crypto and footprint](#crypto-and-footprint)), so passwords are imported.
- **LDAP users** keep the `ldap` source. They can log in once an agent provides `ldap`; until
  then, the login says that the source isn't running.
- **A user orrery already has is left as it is,** since orrery may have changed it since: a
  new password hash after a login, or a logout. orrery's own user with the same name stays,
  and the report names it. `--replace` removes the users that imports wrote, then imports them
  again.
- **Roles aren't imported,** since Moonraker has none. Without `[authorization.users]`, imported
  local users are admin, as they were in Moonraker. The import's report says that, and names the
  users, so the admin can list them by role.

## OIDC (later)

The user's Dex could also log users in directly, with OIDC (user, 2026-11-21). Fluidd's login
form only sends a name and password, and has no "Log in with…" button. orrery could still do it:

1. A page at `/orrery/login` sends the browser to Dex, and Dex sends it back with a code.
2. orrery checks the code with Dex and makes the user's tokens.
3. A page on Fluidd's origin stores the tokens where Fluidd keeps them, `user-token-<md5 of the
   API URL>` and `refresh-token-<md5 of the API URL>` in localStorage
   (`src/store/config/getters.ts:112-117`). Then it goes back to Fluidd.

That depends on Fluidd's storage key names and needs orrery and Fluidd on the same origin, so
any Fluidd release could break it. The clean route is a "Log in with…" button in Fluidd, which
is an upstream change. Until then, proxy logins cover Dex.

**To investigate first** (user, 2026-11-21): how Fluidd's login flows work, and what triggers
each one, so we know which kinds of login orrery can offer without changing Fluidd. OIDC is the
main interest, and it waits until later. Questions to answer from Fluidd's source and by trying
it:

- What makes Fluidd show its login screen, and what makes it skip it: `access.info`'s
  `trusted` and `login_required`, a refused `server.connection.identify`, or a 401 over HTTP.
- What it does with `available_sources` and `default_source`, and whether a source changes
  the form.
- How it uses, refreshes, and drops its stored tokens, and what it does when a refresh fails.
- What happens behind a proxy that logs the user in, such as oauth2-proxy: whether a proxy
  user looks trusted, and what logging out does.
- Whether anything in Fluidd can follow a redirect or open an outside login page, which OIDC
  would need.

## Editing orrery.toml (later)

Roles live in `orrery.toml`, where people can read and review them, and only what can't be in
the config goes in the database: secrets, password hashes, and signing keys (user,
2026-11-21). So giving a user a role means editing `orrery.toml`. Later, orrery could make
that edit itself:

- When an admin adds a user in Fluidd, orrery adds them to `[authorization.users]` under a
  chosen role.
- `orrery user add <name> --role operator` does the same from the CLI, and a matching command
  changes a user's role.

It's out of scope until a UI or the CLI needs to change roles (user, 2026-11-21). These are
the things to settle first:

- **The library.** `toml_edit`, which Cargo uses for `cargo add`, keeps comments, blank lines,
  and key order. `orrery config upgrade` needs it too (see
  [2026-11-22-config-upgrade.md](2026-11-22-config-upgrade.md)), so the two share it. It comes from the same project as the `toml` crate orrery uses, but it's a new
  dependency, and its size needs measuring.
- **Narrow edits only:** one value, or one item in a list. A comment belongs to the item after
  it, so bigger rewrites can leave comments next to the wrong line.
- **Someone else's edit.** A person may be editing the file in Fluidd at the same time. orrery
  refuses to write when the file changed since it last read it, and writes through a temporary
  file and a rename.
- **Reloading.** orrery reads `orrery.toml` once, at startup. An edit needs the changed roles
  reloaded, or it waits for a restart.
- **The backups.** printerkeep and Klipper-Backup commit the config folder to git, so each
  edit becomes a commit. That's a useful record, and one more reason secrets never go there.
- **`moonraker.conf` stays read-only.** There's no comment-preserving editor for its format in
  Rust, and Moonraker never writes it either.

## Config and migration

How Moonraker's login options (`authorization.py:130-150`) map over:

| Option | In this step |
|---|---|
| `force_logins` | Networks give no role; applies whenever set (see [Roles for users](#roles-for-users)) |
| `default_source` | As in Moonraker; also accepts an agent's source |
| `login_timeout` | As in Moonraker: days a refresh token lasts |
| `max_login_attempts` | As in Moonraker, but a lockout ends after `login_lockout` minutes |
| `[ldap]` | Logged as ignored; LDAP waits for an agent |

New in `orrery.toml`: `[authorization.users]`, `default_role`, `local_logins`, `login_lockout`,
and `[authorization.proxy_login]`. The same options in `orrery.toml` win, as everywhere else.

## Crypto and footprint

All pure Rust, with no C dependencies. Sizes are measured on 2026-11-21. They come from a test
program built for `aarch64-unknown-linux-musl` with orrery's release profile. Each crate is
added on its own, on top of `sha2`, which orrery already has:

| Crate | For | Adds |
|---|---|---|
| `ed25519-dalek` 3.0 | Signing and checking tokens | 84 KB |
| `argon2` 0.6 | New password hashes | 27 KB |
| `pbkdf2` 0.13, with `hmac` 0.13 | Imported password hashes | 6 KB |
| All three | | 112 KB |

orrery's binary is 9.4 MB. With step 1 built (local users and tokens), it grew by 234 KB, to
9.6 MB: the crates, plus orrery's own login code. That's about 2.5%. `ed25519-dalek` is already in the workspace,
for `orrery-spoolman`'s TLS. Base64url for tokens uses `base64`, which is in the workspace too.
