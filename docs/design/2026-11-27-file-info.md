# File info

**Status (2026-11-27):** decided with the user, and built: `FileManager::file_info`,
`file_info_map`, and `content_streams` in `crates/orrery/src/files/mod.rs`, with the cases
`conformance/cases/files/file_info.yaml` and `file_info_lists.yaml`. No client uses it yet.

Each file Orrery tells a client about gets a `file_info` block: whether Orrery can print it, as
which format, and the streams a download can give, each with a URL. Clients stop working that
out from the file name.

## Why

Fluidd decides from a list of extensions which files can be printed
(`fluidd/src/store/files/getters.ts:136`, `.gcode .g .gc .gco .ufp .nc`), and takes the
extension after the last dot. Orrery prints more than that list, and that list is fixed in
Fluidd, so it goes wrong (`docs/frontend-issues.md`, `fluidd-extensions`):

- `cube.gcode.3mf` is `.3mf` to Fluidd and `cube.bgcode` is `.bgcode`: no Print button, and
  after an upload no thumbnail or details until a reload. Fluidd asks for a new file's metadata
  only when it knows the extension (`fluidd/src/store/files/actions.ts:116`).
- A reader added in `orrery.toml`, such as `[reader.gx]`, can't be known to any client.
- A file Orrery can't read, such as a broken `.ufp` copied in, looks printable to Fluidd.

Whether a file can be printed is Orrery's call, not the client's (user, 2026-11-27).

## The block

```json
{
  "filename": "cube.bgcode", "size": 15968, "modified": 1795809205.7, "permissions": "rw",
  "file_info": {
    "printable": true,
    "format": "bgcode",
    "url": "server/files/gcodes/cube.bgcode",
    "content": [
      {"kind": "gcode", "name": "gcode", "url": "?content=gcode"},
      {"kind": "original", "name": "original", "url": "?content=original"},
      {"kind": "thumbnail", "name": "thumbnail-32x18", "width": 32, "height": 18, "size": 235,
       "url": "?content=thumbnail-32x18"}
    ]
  }
}
```

- **`printable`:** whether Orrery can print the file now. A gcode file can; a file with a
  reader can, unless reading it failed, and then there's a `reason`, such as
  `"it isn't a binary gcode file"`. Any other file can't, with no reason, and neither can a
  file in another root than `gcodes`.
- **`format`:** the reader that reads it, `gcode` for gcode, and the others by their names:
  `ufp`, `gcode_3mf`, `bgcode`, or one from `orrery.toml`. Left out when no reader is meant for the
  file.
- **`url`:** the file's URL, which its streams' URLs are relative to.
- **`content`:** the file's streams (user, 2026-11-27). The gcode Klipper prints, for a file
  that can be printed; the file as it was uploaded; and each thumbnail. Each has:
  - `kind`: `gcode`, `original`, or `thumbnail`, for a client to pick by;
  - `name`: the value of the download's `content=` (`2026-11-27-file-tools.md`, "What clients
    get"), `thumbnail-<width>x<height>` for a thumbnail. Two thumbnails of one size give one
    stream, the first;
  - `url`;
  - a thumbnail's `width`, `height`, and `size`. The gcode's size isn't known before its cache
    is made, so it has none.

The block is called `file_info`, without a vendor's name, so Moonraker could take it too, which
it should (user, 2026-11-27). The list is `content`, after the query parameter it names the
values of, though what it lists are streams.

## Downloads

`content=` takes the names in the file's `content`, and nothing else: a name the file doesn't
have is refused with 400, which lists the names it has. So `content=gcode` on a file that
can't be printed is refused. Without `content`, a file that can be printed gives its gcode, and
any other gives itself, as before. Moonraker ignores `content`, so either way is harmless there.

`content=thumbnail-32x18` gives the thumbnail, from `.thumbs` for now (user, 2026-11-27). Every
`url` in the list is a `content=` URL, so a client that uses them never needs `.thumbs`, and
Orrery can make thumbnails elsewhere, or on request, later.

## The URLs

The block's `url` is a URL reference, percent-encoded, that the client resolves against the URL
it uses for the server's API, as a browser resolves a link. Each stream's `url` is resolved
against the file's, so it's only the query, `?content=gcode`, and the file's path is in the
block once, which keeps it about half the size (user, 2026-11-27). `new URL(ref, base)` does
both steps. For both (user, 2026-11-27):

- **No leading slash**, so it also works when a client reaches the server under a path, such as
  `https://host/printer1/`.
- **The server owns it.** It can be an absolute URL later, and a client that resolves it needs
  no change.
- **The client doesn't build it.** Fluidd builds a thumbnail's URL from `relative_path`, and
  encodes each part of it, so a query in it can't survive.

Each part of the path is encoded on its own: `a b/my cube.gcode` is
`server/files/gcodes/a%20b/my%20cube.gcode`. The metadata's `thumbnails`, with `relative_path`,
stay as they are, for clients written for Moonraker.

## Where it appears

Wherever a client hears of a file, so it never has to guess:

- each file in `server.files.get_directory`, with `extended` or without, and in
  `server.files.list`, when the client asks with `file_info: true`. On bluev2, with 752 files,
  the blocks were 437 KB of Fluidd's 1.34 MB jobs listing, which Fluidd doesn't read, so
  listings have them only on request (user, 2026-11-27);
- history and the job queue, as a map (below);
- `server.files.metadata`'s and `server.files.metascan`'s results;
- a file's `item` in `notify_filelist_changed`, and in the replies of uploads, copies, and
  moves. This is the one Fluidd needs, so a new file shows its thumbnail without a reload. A
  file the watcher found has the thumbnails read by the time it's announced.

It's worked out from what Orrery holds already, the readers and the stored metadata, with no
reading of the file. A listing reads each file's stored metadata once, for both the metadata
and the block. Why a file couldn't be read is kept with
its metadata, under a key clients don't get, so it's still known after a restart.

## Lists that name files

History and the job queue name files too, and a client needs to know whether it can print one
again (user, 2026-11-27). They can be long, and name one file many times: a file printed twenty
times is twenty history entries. So the block isn't in each entry. The result has one
`file_info` map, keyed by the file's name, with each file once:

```json
{"count": 3, "jobs": [{"filename": "cube.gcode", ...}, {"filename": "cube.gcode", ...}, {"filename": "lid.bgcode", ...}],
 "file_info": {"cube.gcode": {...}, "lid.bgcode": {...}}}
```

- `server.history.list`, and `server.history.get_job`, with its one file;
- `notify_history_changed`, next to its `job`;
- `server.job_queue.status`, and the replies of the queue's other requests, next to
  `queued_jobs`;
- `notify_job_queue_changed`, when it has an `updated_queue`.

A file that isn't there any more is `{"printable": false, "reason": "the file doesn't exist any
more"}`, with nothing to download. History's `exists` is Moonraker's, and says whether the file
is the one that was printed; the map is about the file at that name now.

The tests' `$exact` and the snapshot check allow `file_info` as one of Orrery's additions
(`crates/conformance/src/matcher.rs`, `ADDITIONS`).

## Not in it

- **Whether a file can be edited** (user, 2026-11-27). What an editor can change is the tool's
  business. Fluidd's editor shows a `.bgcode`'s gcode, and its Save is refused.
