# File info

**Status (2026-11-27):** proposed, with the name and the fields decided with the user. Not
built.

Each file Orrery tells a client about gets a `file_info` block: whether Orrery can print it, as
which format, what a download can give, and where its thumbnails are. Clients stop working that
out from the file name.

## Why

Fluidd decides from a list of extensions which files can be printed
(`fluidd/src/store/files/getters.ts:136`, `.gcode .g .gc .gco .ufp .nc`), and takes the
extension after the last dot. Orrery prints more than that list, and that list is fixed in
Fluidd, so it goes wrong:

- `cube.gcode.3mf` is `.3mf` to Fluidd and `cube.bgcode` is `.bgcode`: no Print button, and
  after an upload no thumbnail or details until a reload. Fluidd asks for a new file's metadata
  only when it knows the extension (`fluidd/src/store/files/actions.ts:116`).
- A reader added in `orrery.toml`, such as `[reader.gx]`, can't be known to any client.
- A file Orrery can't read, such as a broken `.ufp` copied in, looks printable to Fluidd.

Whether a file can be printed is Orrery's call, not the client's (user, 2026-11-27).

## The block

```json
{
  "filename": "cube.bgcode", "size": 15968, "modified": 1795809205.7, "permissions": "rw",
  "file_info": {
    "printable": true,
    "format": "bgcode",
    "content": ["gcode", "original"],
    "thumbnails": [
      {"width": 32, "height": 18, "size": 235, "url": "server/files/gcodes/.thumbs/cube.bgcode-32x18.png"}
    ]
  }
}
```

- **`printable`:** whether Orrery can print the file now. A gcode file can; a file with a
  reader can, unless reading it failed, and then there's a `reason`, such as
  `"it isn't a binary gcode file"`. Any other file can't, with no reason. A file in another root
  than `gcodes` can't.
- **`format`:** the reader that reads it, `gcode` for gcode, and the others by their names:
  `ufp`, `3mf`, `bgcode`, or one from `orrery.toml`. Left out when the file isn't printable and
  no reader is meant for it.
- **`content`:** the values a download takes in `content=`
  (`2026-11-27-file-tools.md`, "What clients get"): `["gcode", "original"]` for a file that can
  be printed, `["original"]` for any other.
- **`thumbnails`:** the file's thumbnails, each with a `url`.

## Thumbnail URLs

Each `url` is a URL reference, percent-encoded, that the client resolves against the URL it
uses for the server's API, as a browser resolves a link (user, 2026-11-27):

- **No leading slash**, so it also works when a client reaches the server under a path, such as
  `https://host/printer1/`.
- **The server owns it.** It can be an absolute URL later, or point at a query such as
  `?content=thumbnail-32x18` (`2026-11-27-file-tools.md`, "Thumbnails, later"), and a client
  that resolves it needs no change.
- **The client doesn't build it.** Fluidd builds a thumbnail's URL from `relative_path`, and
  encodes each part of it, so a query in it can't survive.

The metadata's `thumbnails`, with `relative_path`, stay as they are, for clients written for
Moonraker.

## Where it appears

Wherever a client hears of a file, so it never has to guess:

- each file in `server.files.get_directory`, with `extended` or without, and in
  `server.files.list`;
- `server.files.metadata`'s result;
- the `item` of `notify_filelist_changed`, for `create_file`, `modify_file`, and `move_file`,
  and the upload's reply, which has the same `item`. This is the one Fluidd needs, so a new file
  shows its thumbnail without a reload.

It's worked out from what Orrery holds already, the readers and the stored metadata, with no
reading of the file, so listing a folder costs no more.

## Not in it

- **Whether a file can be edited** (user, 2026-11-27). What an editor can change is the tool's
  business. Fluidd's editor shows a `.bgcode`'s gcode, and its Save is refused.

## Compatibility

Clients written for Moonraker ignore a key they don't know, so `file_info` is harmless to them.
The name has no vendor in it, so Moonraker could take the block too, which it should (user,
2026-11-27). A client that knows the block uses it when it's there, and its own rules when it
isn't.

## Open questions

- **Should a download refuse `content=gcode` for a file that can't be printed**, now that
  `content` says which values work? Today it gives the file as it is. Moonraker ignores
  `content`, so either is harmless there.
- **History and the job queue** name files too. Their entries could carry the block, or a
  client could ask `server.files.metadata`.
- **Proposing it to Moonraker and Fluidd**, once it's built and used.
